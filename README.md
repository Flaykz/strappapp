# Strapp

MVP local Preact + TypeScript pour préparer les bandes de Strappal.

## Démarrer

```sh
npm install
npm run dev
```

Ouvrir l’adresse indiquée par Vite (par défaut http://localhost:5173).

`npm run build` vérifie TypeScript et produit `dist/`. `npm test` vérifie le calcul de découpe.

## GitHub Pages

Le workflow `.github/workflows/pages.yml` teste et compile l’application puis la déploie sur GitHub Pages à chaque push sur `main`. Il peut aussi être lancé manuellement depuis l’onglet Actions. Dans Settings → Pages, choisir GitHub Actions comme source. Un dépôt privé nécessite une offre GitHub compatible avec Pages ; sinon, le dépôt doit être public.

Adresse prévue : `https://flaykz.github.io/strappapp/`. Le workflow compile avec `npm run build -- --base=/strappapp/` pour charger les ressources sous le chemin du dépôt.

## Fonctionnement

Le protocole et le matériel sont sauvegardés dans le stockage local du navigateur. Export/import JSON pour sauvegarder ou transférer les données. Les exemples initiaux ne sont pas des recommandations de soin.

La largeur du rouleau vient uniquement du stock : « Ton matériel » propose un sélecteur du type de rouleau (largeur en lecture seule, à modifier dans « Mon stock de rouleaux »). Sans type de rouleau, l’app invite à en créer un et utilise provisoirement la largeur `roll` du protocole. Le champ `roll` du protocole (export/import) est maintenu égal à la largeur du type sélectionné ; à l’import, un type de même largeur est présélectionné s’il existe, sinon la largeur du type sélectionné reste appliquée et un message le signale. Une bande normale fait la moitié de la largeur du rouleau, une bande « Largeur entière » toute la largeur : il n’y a plus de réglage de largeur des bandes. Le nombre global de séances à préparer multiplie le protocole entier. Chaque bande conserve son nom, sa longueur, son côté et l’option « Largeur entière » (champ optionnel `fullWidth`, absent par défaut). Les anciens champs de largeur (`bandWidth` global, `width` par bande) sont tolérés à la lecture mais ignorés et jamais réécrits. Une copie de l’ancien format local est conservée sous `strapp-protocol-before-global-settings` lorsque le stockage le permet. Les exports utilisent le champ global `sessions`. Les anciennes quantités identiques deviennent le nombre de séances ; si elles diffèrent, le nombre est fixé à 1 avec un message explicatif.

Les bandes sont posées dans l’ordre exact du protocole (séance, bande, côté), en lisant la plaque de gauche à droite puis de haut en bas. La longueur de la plaque est l’axe horizontal. Une ligne est un morceau de rouleau déroulé de gauche à droite, de la largeur du rouleau. Les pièces consécutives (dans l’ordre du protocole, y compris de bandes différentes, quel que soit le côté) qui ont exactement la même longueur et la même largeur sont superposées dans la largeur du rouleau, dans la limite de la largeur du rouleau divisée par celle des pièces (deux pour une demi-largeur, une pour une bande entière) ; une bande Gauche seule suivie d’une bande Droite seule de même longueur tiennent donc ensemble. Avec « Gauche + droite » suivie d’une bande de même longueur, l’empilement est glouton : G de la première, puis ce qui reste se répartit dans l’ordre. Une bande « Largeur entière » fait toute la largeur du rouleau : ses pièces ne sont jamais superposées (avec « Gauche + droite », une bande entière G puis une D, bout à bout) et ne demandent pas de coupe horizontale. Les segments se suivent bout à bout, sans écart ; quand le suivant ne tient plus dans la longueur restante, une nouvelle ligne commence en dessous, avec 1 cm d’écart. Quand la plaque est pleine, un nouveau passage commence. Il n’y a ni réordonnancement ni retour en arrière. Le plan affiche une graduation sur les bords haut et gauche (trait tous les cm, trait long tous les 5 cm, chiffre tous les 10 cm), la cote de chaque coupe verticale et la position des lignes et des coupes horizontales sur le bord gauche. Les schémas sont proportionnels, pas des gabarits imprimables à taille réelle.

L’ordre des lignes du protocole est l’ordre de pose. Chaque séance inclut une bande par côté sélectionné pour chaque ligne. Deux séances préparent deux jeux complets. Sans compte, aucune donnée du protocole n’est envoyée à un serveur (voir « Synchronisation »).

L’application est une PWA installable. Après une première ouverture en ligne, son interface reste disponible hors connexion ; les modifications locales et les tentatives de synchronisation reprennent normalement au retour du réseau. Sur Android/Chrome, utiliser « Installer l’application ». Sur iPhone/iPad/Safari, utiliser Partager → « Sur l’écran d’accueil ».

## Coupes

Pour chaque ligne, dans l’ordre : coupes horizontales entre les pièces superposées, puis coupes verticales aux frontières entre segments, la dernière détachant la ligne du rouleau. Les coupes sont listées ligne par ligne, de gauche à droite, sans optimisation de parcours. Le plan suppose le maintien de tous les morceaux à leur place jusqu’à la fin.

Le stock est conservé séparément du protocole (hors export). Un type standard de 4 cm × 10 m est proposé ; on peut ajouter des types et saisir le reste de chaque rouleau. Chaque ligne (un morceau de rouleau de la longueur de la ligne) est attribuée au rouleau compatible ayant le plus petit reste suffisant. La consommation s’enregistre **par passage**, une fois ses découpes réalisées : le bouton « Enregistrer la consommation de ce passage » (au-dessus du plan) ne décompte que les lignes du passage affiché, et la navigation des passages marque d’un ✓ ceux déjà enregistrés. « Annuler l’enregistrement » rend exactement les longueurs consommées aux mêmes rouleaux (si un rouleau a été retiré entre-temps, un message signale la longueur non restituée). L’allocation affichée tient compte des passages déjà enregistrés, le stock étant déjà diminué. Le suivi est stocké dans le stock lui-même (`stock.preparation = { key, passes: { [index]: { recordedAt, consumed: [{ rollId, length }] } } }`), donc il survit au rechargement, à l’ajustement d’un reste et il est synchronisé avec le stock. `key` est une empreinte du plan (séances, largeur du rouleau, plaque, identifiant, longueur et côté des bandes ; pas les noms). Si l’empreinte change, le suivi repart à zéro : les passages déjà enregistrés restent décomptés du stock et un avertissement l’indique.

## Synchronisation

Optionnelle : l’app reste entièrement utilisable sans compte et hors ligne, le stockage local restant la source locale. Le panneau « Synchronisation » (onglet « Mon protocole ») permet de se connecter avec un email et un mot de passe ; il n’y a pas d’inscription, le compte est créé par l’administrateur du serveur PocketBase (`https://pb.flaykz.ovh`, surchargeable avec `VITE_PB_URL` au build). La session est conservée sur l’appareil : une connexion par appareil suffit.

Deux documents sont synchronisés avec la même mécanique, dans deux collections PocketBase (un enregistrement par utilisateur, même schéma : `owner`, `data` JSON, `clientUpdatedAt`) : le protocole (même format que l’export JSON) dans `protocols`, et le stock (types, rouleaux, suivi de préparation) dans `stocks`. Une seule connexion et un seul panneau ; chaque document a ses propres métadonnées locales (`strapp-sync-meta` pour le protocole, `strapp-sync-meta-stock` pour le stock), son envoi différé et son état. Chaque modification locale met à jour l’horodatage du document concerné (`clientUpdatedAt`) et le marque « non envoyé » ; l’envoi est différé d’environ 1,5 s. À l’ouverture, au retour de focus et au retour de connexion, l’app compare les horodatages document par document : la version la plus récente gagne (le stock est donc remplacé en bloc : deux appareils qui modifient le stock en même temps, le dernier envoi l’emporte). Les données distantes sont validées avant de remplacer le local (comme un import pour le protocole, décodeur dédié pour le stock) ; des données invalides sont rejetées avec un message. À la première connexion d’un appareil, la version en ligne la plus récente remplace les données locales ; celles-ci sont copiées au préalable dans `strapp-protocol-before-sync` (format `{ savedAt, protocol }`) ou `strapp-stock-before-sync` (format `{ savedAt, stock }`), récupérables via la console du navigateur. La copie n’est faite que si le local a des modifications non envoyées (ou n’a jamais été synchronisé) et diffère du distant ; une copie de moins de 24 h est conservée, sinon elle est remplacée. Hors ligne ou en cas d’erreur réseau ou serveur, les modifications restent en attente et sont renvoyées automatiquement (reprise après 30 s, 1 min, 2 min, puis toutes les 5 min) ou dès le retour de focus. Si la session expire, le panneau repasse à « Non connecté » : les modifications restent en attente et partent après reconnexion. Si la collection `stocks` n’existe pas encore sur le serveur (404), la synchronisation du stock échoue avec un message clair (« Stock : Collection absente du serveur… »), sans nouvelle tentative automatique et sans bloquer celle du protocole ; elle reprend au prochain focus une fois la collection créée. Les horloges des appareils font foi : une horloge très décalée peut fausser l’arbitrage.

Le stock est synchronisé en bloc (le plus récent gagne) : enregistrer des passages sur deux appareils hors ligne en même temps peut faire perdre l’un des enregistrements. Synchronise avant de découper sur un autre appareil.
